
# Team Workflow

## Meetings

We meet twice a week for approximately 2–3 hours each session. Meetings are used for planning, coordinating tasks, and discussing progress. They are also working sessions where we code together, solve problems as a group, and occasionally do pair or group programming. Some members also meet outside the dedicated group meetings to work together, while the rest of the work is done individually. Quick coordination outside meetings is handled via Facebook Messenger.

## Task Management

We manage tasks using GitHub Issues, Milestones, and the Project view with a Kanban board.

For each new release, the first meeting is used to create all relevant GitHub issues and define user stories when applicable. (For release 1, user stories were defined; for release 2, the focus is on refactoring, documentation, and testing.) Each new release gets a new Milestone (e.g. Release1 or Release2).

Assignees are used for GitHub issues. Team members pick tasks themselves using a “first come, first serve” approach, with the expectation that workload is fairly distributed. This trust-based system has worked well for our small team.

The team does not separate into backend/frontend sub-teams, as the project size does not justify this division.

## Documentation & Tools

Google Drive and Docs is used to structure todos and store meeting notes before tasks are entered into GitHub issues.

All code should be documented by the person who writes it.

Team templates in [/.github](../../.github) include [issue_template.md](../../.github/issue_template.md) and [pull_request_template.md](../../.github/pull_request_template.md) for consistency.

## Commit & PR Conventions

We follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) for consistent commit messages.

All issues, pull requests, commits, and code documentation follow the same structure to maintain clarity and traceability.

Every pull request requires at least one reviewer before it is merged.
